# Acceptance tracking

When work is guided by an acceptance checklist, add newly discovered gaps to the relevant checklist as distinct, actionable, unchecked items. Explain how each gap relates to the existing requirement, and distinguish a breakdown of an existing requirement from newly expanded scope.

Keep checklist status and related documentation current as work progresses. Mark an item complete only when its stated implementation, tests, demonstrations, and evidence have actually been completed; record the evidence and any remaining limitations. Keep parent items open until their acceptance criteria are met.

When reporting work for acceptance, show the relevant checked and unchecked items, and demonstrate the change live in the application when the user has requested a demonstration. Clearly state when a demonstration has not happened or the change is not yet available in the app.

For patch-posture Phase 4, follow the agreed execution order recorded in `docs/patch-posture-phase-acceptance.md`. Keep the current P4-08b identity/permissions work first, and retain deferred host requirements as open prerequisites.
