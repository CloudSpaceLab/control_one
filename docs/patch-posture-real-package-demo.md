## What was actually done

1. Confirm Local Development tenant `91fc1ed4-fb36-4fcf-91e6-a4d0f4eebe7f` and lab node `d033fa85-5796-48ae-8e8a-f82706387326`. Check the installed and candidate versions using Ubuntu's package metadata. A simulated `apt-get --only-upgrade install perl-base` showed **one upgrade, zero new installations and zero removals**. The other four available upgrades were outside this request.
2. Save image `controlone-phase0-patch-lab:20261020-before-real-package`, image ID `sha256:addea40507bff6595f4b082923ce112fc4cd9f742ea4ecb8de0030b407322587`. Verify the old Perl version in a network-disabled instance with a read-only package-query entrypoint. Enrolled recovery images contain credentials; do not publish them or run duplicate agents with the same identity.
3. Prepare repository access without attaching the lab to an external Docker bridge. Use a separate temporary Squid container, permitting only the lab IP `172.19.0.3`, GET/HEAD methods and `archive.ubuntu.com` / `security.ubuntu.com`; deny everything else. No host port was published. Refresh Ubuntu metadata through this proxy with normal APT signature verification enabled.
4. Register proxy `5754e4d8-b7ac-496e-a5be-60143dd64c7a`, endpoint `http://phase0-repo-proxy:3128`, through the authenticated local API and assign it only to this lab. This administrative repository setup used a terminal; the deployment request and approval were performed in the visible app.
5. Run the read-only Control One plan with one node, `package_allowlist: ["perl-base"]`, `post_patch_rescan: true`, and proxy mode. It returned **approval_required**. The package allowlist is essential: an empty allowlist permits all eligible packages.
6. In the app, open **Patch posture → Deploy patches…**. Enter `perl-base` in **Package allowlist**, retain **Refresh package inventory after patching**, select only **phase0-ubuntu-lab**, and enter the reason. This run used **auto (per-node config)**, which resolved to the lab's proxy mode. Submit the request and open **Approvals**.
7. Approve the new lab request. Approval `c33b17f3-b6a7-4b7f-b0a5-57b3d7d012de` carries the policy hash. Deployment `627aeee3-6106-4169-979d-2d63e123b63e` created job `965968ae-5f1c-40bc-8816-f5d84cfdefce`, type `patch.deploy_proxy`, carrying only the allowed package. The agent ran the existing apt execution path; no manual `dpkg -i` or substitute package upgrade was used.
8. Wait for the next heartbeat to deliver the job and a later heartbeat to persist the completion. Execution began at `12:15:45 UTC` and reported success at `12:15:52 UTC`. The dpkg log records `Unpacking perl-base (5.38.2-3.2ubuntu0.6) over (5.38.2-3.2ubuntu0.4)` and successful setup. The durable agent journal records the result and `acknowledged: true` after server persistence.
9. Refresh **Patch posture**, then inspect the deployment: **Completed**, **1/1 applied**. Open **Servers → phase0-ubuntu-lab → Packages**, disable **Hide system packages**, and filter `perl-base`. The new version appears with source **dpkg**. Also verify directly with `dpkg-query -W perl-base` on the target.

## Defects found and their disposition

- The UI originally exposed no package selection despite API/agent support. Added **Package allowlist** and the inventory-refresh checkbox, with dependency/scope guidance. A UI regression test verifies one selected node, deduplicated package names and the rescan flag. All eight patch-page tests passed; TypeScript checks passed.
- Quiet apt output omitted the summary expected by the upgrade counter. The first real deployment therefore correctly completed but recorded **0** in `PackagesUpgraded`. The version change and dpkg log prove the actual upgrade. Fixed the parser to count unique `Unpacking ... over (old-version)` records while excluding fresh installations and no-op runs. Focused Go tests passed, including a regression test using the actual observed line. Built and deployed the corrected Ubuntu agent as `phase1-quiet-apt-fix-7f3a75ee`; the original completed report is preserved without manual rewriting. The corrected counter was tested against real captured output, not a second real upgrade.
- The deployment batch header displayed **direct** when the request used **auto**, although the actual node plan, approval, queued job and executed command used **proxy**. This existing display/model limitation remains open. For a repeat run, select **proxy** explicitly after configuring a valid proxy, and verify the read-only plan before submission. Do not infer the executed transport from that old batch header.

The package is now current for the metadata used in this demonstration. Repeating the same request now may upgrade zero packages legitimately. For a fresh client demonstration, prepare a separate disposable target with a known older supported version and a tested recovery checkpoint; do not downgrade a live client system merely to create a demonstration.
