## What makes the path pass

There are two different checks. Automated software tests must prove transaction safety, authority, scope, timing, deduplication, failure handling and canary guards. The actual target must also report current authoritative observations. A passing fixture does not turn missing real-host evidence into a pass.

Required observations include a healthy native package audit, complete healthy service observations, complete consumer checks, known boot identity, no pending reboot, current authoritative inventory and a current selected-advisory assessment. ## Operator procedure

1. Open **Patch posture → Review policy & ownership**, select the tenant and expand **Explicit automation policy draft**. Preserve explicit node/canary/package/exclusion/window/transport/wave scope and choose a future policy expiry.
2. In **Scheduled and automatic execution checks**, use **Use native service/reboot requirements** and set the canary observation period. The fixed profile name is a required contract, not proof that observations passed.
3. Click **Test selected targets for automation readiness**. This is read-only and returns each actual hostname and blocking reason. A change to scope/profile/window invalidates the UI readiness result; results also expire. Correct the cause on a suitable supported host and check again. Do not change unknown health to healthy merely to clear the gate.
4. Only after readiness passes can the administrator request enablement. **Save operational controls** requires a separate activation confirmation. The server rechecks target health and window membership/status; stale policy revisions conflict. Drafts remain disabled by default. An invalid or expired policy does not authorise installation.
5. Prepare a fresh exact plan and create its normal pending patch approval through the existing deployment workflow. Preparation acquires package bytes but installs nothing. Plans last at most one hour; a distant maintenance window needs fresh preparation near its start. The schedule cannot outlive its plan, approval, window or policy.
6. For a canary, select **Pending exact approval**, enter **Execute no earlier than (UTC)**, then **Review exact schedule authorization**. Confirm **Approve and schedule exact request** only after reading its exact request, policy revision and date. Canary execution always requires this individual authorization, including under automatic mode.
7. The durable minute scheduler processes due retained requests. Waiting/blocked is not installed. Dispatch checks current policy/authority, exact plan identity, runtime/source/transport/calendar gates, health and assessment, and commits the approval, execution job, state/action-plan links and authorization receipt together. The same checks are applied again by the agent's authorization call under the APT lock. A policy disable/change or revoked user authority prevents a later start; a package manager already running is not force-killed.
8. Approved-scheduled targets remain individually authorised. Narrow automatic mode can select existing pending exact requests only inside the enabled policy, and only when individual approval is explicitly not required. It never automatically starts a canary. Later targets require every designated canary to have a current verified fix/removal, complete health/reboot evidence and the observation period. They must match acquired package bytes, requested/resolved versions and dependency scope, and source/trust inputs. Empty or old archive-identity evidence blocks automatic promotion.
9. Failed/cancelled execution or failed verification trips the policy revision's circuit breaker. Unknown, expired or incomplete previous-wave verification also blocks further waves. Queued/running executions count against the maximum wave size. Failed, cancelled, expired or uncertain executions are not automatically replaced with new requests or blindly replayed. Review evidence and create a new explicit policy revision/exact request when a safe recovery is established.
10. **Refresh scheduled requests** shows the latest 100 retained authorizations and current reasons. **Cancel undispatched schedule** withdraws only waiting/blocked work. **Stop installation automation** saves recommendation-only and disables the policy, including when an old installation draft has expired. Neither operation promises to interrupt an already-running package manager.

## Boundaries and retention

Migration **0178** adds durable scheduled execution authorizations. One retained schedule is allowed per approval; duplicates do not manufacture a new package job. Cancellation leaves history intact. Policy revisions, not mutable labels alone, bind the authority. No scheduled request can strip its retained authorization and use ordinary immediate approval dispatch instead.

The scheduler checks at most 25 due requests per minute, ordered by last check so blocked due requests rotate. Automatic discovery inspects a bounded 25-candidate batch; intended-fleet discovery throughput and backlog/fairness qualification remain open under Phase 5. Scope currently covers exact APT online plans for Ubuntu direct/proxy modes. Airgapped scheduled installation, Windows/dnf/yum automatic execution, arbitrary external health probes, automatic advisory discovery/preparation, and production fleet/soak qualification are not included. The automatic scheduler consumes already-prepared exact requests; it does not choose arbitrary newly available versions. The policy must be requalified before extending this scope.
