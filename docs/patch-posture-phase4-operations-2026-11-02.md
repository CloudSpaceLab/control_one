## How to use the workspace

Open **Patch posture → Review policy & ownership** with the correct tenant selected.

1. Use **Records per page**, **Next findings** and **Previous findings** to browse the active review queue. History has separate older/newer controls. Stable finding IDs and event IDs are the cursors; changing the page size resets both cursors. Refresh retains the selected page. Each page is a current database snapshot, so concurrent additions/resolutions may change later pages; use an export for a single consistent evidence snapshot.
2. Click **Export review evidence**. The download contains all active findings, all review tracking, all retained review events, all approval history, operational policy and escalation delivery receipts in one repeatable-read database snapshot. The UI history visibility window does not discard older retained events from this export. Inspect `format: 2`, the tenant ID, `event_scope: all_retained`, section `counts` and `complete: true`. The UI displays its archive ID and SHA-256. Verify the downloaded bytes against that SHA-256 and retain the archive in the organisation's approved evidence destination.
3. Enter an accountable **Operations owner/team** and **Operations change reason**. Changes require administrator access and an explicit **Save operational controls**. Revision conflicts require reloading and reviewing the newer policy.
4. Expand **Evidence retention and legal hold**. Defaults retain all history with legal hold enabled. Save the chosen retention policy before **Preview retention batch**. A preview is read-only and shows the exact eligible count, cutoff, digest and any blocking hold. It covers at most 1,000 historical review events per batch, excluding current revisions, findings, approvals and installation receipts. It does not delete anything automatically.
5. Where deletion is organisationally approved, choose archive-then-purge, remove the legal hold deliberately, save, download/verify/retain a complete archive, then produce a fresh preview. Supply the archive ID, retained destination and explicit verification acknowledgement. The app requires a final destructive confirmation. The server rechecks the saved revision, hold, retention cutoff, preview digest and a recent same-administrator archive covering the entire batch. A changed preview, wrong tenant/actor, missing archive or expired receipt blocks deletion. A durable purge receipt remains. **Do not purge live history merely to demonstrate this feature.** Positive and negative purge cases were tested only in the isolated test database.
6. Expand **Escalation notification handling**. Select explicit currently authorised tenant recipients and a repeat interval. **Notify only my account** is suitable for a private demonstration. Enable the channel, save, and use **Run saved escalation check**, or allow the minute scheduler to check. It notifies on unassigned finding reviews, explicit overdue review dates and expired exceptions. This channel is the Control One notification bell; email, SMS and webhooks are not configured by this feature. Free-text escalation team labels do not grant access or establish external destinations.
7. Open the bell and follow a patch review notification to this workspace. Notification and deduplication receipt are committed together. Concurrent workers and retries do not duplicate the same finding/review/policy within the configured rolling interval; changing the reviewed finding or operational policy intentionally creates a new revision. Recipient access is rechecked when delivering. Delivery errors remain visible and retry on later checks. Disable the channel and save after a self-only demonstration if ongoing notifications are unwanted.
8. Expand **Explicit automation policy draft**. Recommendation-only remains effective. For an approved-scheduled or narrowly automatic draft, select explicit active tenant targets, canaries within that scope, package names, exclusions, an existing tenant window, transport, maximum wave size, a declared health/recovery requirement and a UTC expiry within 90 days. The server verifies target ownership and window membership. Approved-scheduled drafts require individual approval; exact-plan, fresh-assessment, health, reboot and failure-stop requirements cannot be removed. A declared health profile is a review requirement, not a qualified probe. Both installation modes are stored **disabled**, have no activation button and create no jobs or approvals. An API attempt to activate them is rejected pending Phase 5 execution and promotion qualification.
