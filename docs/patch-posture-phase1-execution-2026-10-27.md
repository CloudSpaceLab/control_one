## First fixes: journal consistency and acknowledgment persistence

Two isolated regressions reproduced defects in the existing candidate:

1. The journal accepted valid JSON with inconsistent execution evidence: empty job identity, a non-patch action, an acknowledged reservation with no result, a result belonging to another job/action, or a nonterminal result. All six cases were accepted before this change. Startup could rewrite that evidence or suppress a result instead of stopping for reconciliation.
2. A failed acknowledgment write left `Acknowledged=true` in memory even though the file had not changed. The result stopped appearing in the current process's pending reports. The server may already have persisted the result, so this does not establish server-side data loss; it is an inconsistent local persistence/retry contract.

`cmd/nodeagent/patch_journal.go` now validates every loaded entry before any recovery rewrite. Invalid evidence returns an error without changing the file. Reservation/completion writes use the same identity/status checks. Genuine interrupted, unacknowledged reservations still become an explicit unknown-outcome failure requiring reconciliation, and remain reserved against automatic rerun.

Acknowledgment changes are rolled back in memory when persistence fails. Duplicate acknowledgment IDs cannot defeat that rollback. The agent retains the pending result, can retry the acknowledgment, and keeps its execution reservation after successful acknowledgment/restart.

The existing startup behavior treats an unusable journal as fatal for the agent. This change extends that existing fail-closed behavior to semantic corruption; it does not introduce a separate patch-only degraded mode. Preserve a rejected file for operator investigation. Deleting it to bypass the check can discard execution reservations and permit unsafe re-execution.

## Completion recovery hardening — 27 October 2026

This continuation fixes the previously documented gap between core completion and its receipt/deployment summary. Migration 166 adds patch_completion_effects, a per-job durable acknowledgment marker. CompletePatchJob now commits node state, job state, terminal event, action receipt, action-plan state, parent summary and marker in one transaction. The parent row lock serializes summary calculations across different nodes; approval outcomes use the same locked summary path. A matching legacy terminal retry without a marker reconciles missing effects using saved package count/log/error, rather than changed retry metadata. A fully committed retry avoids rewriting receipts and timestamps. Acknowledgment requires the marker, so a failed receipt/summary/marker write cannot suppress the agent's retained result.

Dispatched patch jobs now reject the generic cancellation endpoint with HTTP 409 for direct, proxy and airgapped actions. Marking a database row cancelled cannot stop an OS package-manager command and can race away its real outcome. Approval denial before dispatch remains available; this safeguard does not add operating-system process cancellation.
